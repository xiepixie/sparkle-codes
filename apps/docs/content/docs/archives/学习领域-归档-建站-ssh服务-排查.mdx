# 📝 探究记录：SSH 握手后立即断开 (TUN 模式代理引发的血案)

## 📌 1. 故障现象描述

在使用 `ssh -vvv root@<Server_IP>` 连接远程 Linux 服务器时，连接在 TCP 三次握手成功后，于 SSH 协议层面的“版本交换/密钥交换”阶段瞬间断开。

**核心报错日志片段：**
```text
debug1: Connection established.  <-- TCP 三次握手成功
...
debug1: Local version string SSH-2.0-OpenSSH_10.2  <-- 本端发送 SSH 版本号
kex_exchange_identification: Connection closed by remote host  <-- 远端未响应版本号，直接掐断连接
Connection closed by 154.36.155.185 port 22
```

## 🔍 2. 初始排查与服务端假设（常规思路）

在未发现本地网络环境存在特殊配置前，基于日志表现（TCP通，SSH协议不通），首先推测是**服务端主动拒绝了连接**。常规排查方向如下：

1.  **IP 封禁 (Fail2ban)：** 最常见。TCP 握手由内核直接处理（成功），但当请求传递给应用层（SSHD）时，由于源 IP 在 `iptables` 或 `fail2ban` 的黑名单中，数据包被 Drop 或 Reject。
2.  **并发数超限 (MaxStartups)：** 服务器遭受 SSH 爆破，处于未经身份验证的连接数超过了 `sshd_config` 中的限制，SSHD 进程主动拒绝新的协议握手。
3.  **TCP Wrappers 限制：** `/etc/hosts.deny` 拦截了该 IP 段。
4.  **SSHD 进程异常：** 进程假死或内存溢出，内核层面 TCP 保活，但应用层无响应。

**但真实情况推翻了以上所有假设：服务端一切正常，问题出在客户端本机的“网络代理 TUN 模式”。**

---

## 🚀 3. 深入剖析：为什么 TUN 模式会导致该故障？

在运行诸如 Clash、Surge、V2rayN 等代理软件的 **TUN（Tunnel）模式** 时，代理软件会在操作系统中创建一张**虚拟网卡**（Layer 3 接口），并接管系统的全局路由表，将所有目标为公网的 IP 数据包强制路由到这个虚拟网卡。

这导致了网络数据流的本质改变，具体引发报错的机制如下：

### 剖析一：虚假的 `Connection established` (TCP 代理截断)
在 TUN 模式下，本地 SSH 客户端并没有真正和远端服务器（154.36.155.185）建立物理上的端到端 TCP 连接。
1.  SSH 客户端发出 `SYN` 包。
2.  TUN 虚拟网卡截获该包，代理软件的内核（如 Clash Core）**代替远端服务器，直接向本地 SSH 客户端回复了 `SYN+ACK`**。
3.  SSH 客户端回复 `ACK`。此时终端打印出 `debug1: Connection established.`。
**结论：** 此时的 TCP 握手，仅仅是 **SSH 客户端与本地代理软件核心** 之间建立的。SSH 客户端被“欺骗”了。

### 剖析二：上游节点策略拦截 (Port 22 阻断)
当本地 TCP 连接建立后，SSH 客户端发出了带有 `SSH-2.0-OpenSSH_10.2` payload 的数据包。
1.  本地代理核心收到这个 payload，准备将其封装（如使用 Shadowsocks/VMess 协议）发送给**远端代理节点（Proxy Server）**。
2.  代理节点收到请求，尝试去连接真实的 SSH 服务器（154.36.155.185:22）。
3.  **【致命点】**：绝大多数商业机场或公共代理节点，为了防止用户利用他们的服务器去进行 SSH 暴力破解或发起 DDoS 攻击，**会在代理服务端的防火墙上严格封锁 22、25（邮件）、445 等高危端口**。
4.  由于 22 端口被代理节点拒绝，代理节点向本地代理软件返回连接失败的错误（如 `connection refused` 或直接超时）。
5.  本地代理软件收到错误后，只能向本地的 SSH 客户端发送一个 `TCP FIN` 或 `RST` 包。
6.  SSH 客户端收到断开信号，打印出 `Connection closed by remote host`。

### 剖析三：协议嗅探与路由规则匹配失败 (Routing Leak/Drop)
部分高级代理软件开启了 **DPI（深度包检测）** 或 **Sniffing（协议嗅探）**。
它们期望通过嗅探出 HTTP Host 或 TLS SNI 来进行域名规则分流。当代理核心截获到 SSH 数据流时，发现既不是 HTTP 也不是 TLS，嗅探失败，可能会触发默认的“漏网之鱼”规则。如果默认规则配置为 `Reject`（拒绝）或路由到了一个不支持 UDP/TCP 纯流量转发的节点，连接同样会瞬间中断。

## 🛠️ 4. 解决方案与最佳实践

作为网络专业人员，在使用代理时，应避免粗暴地全局开启 TUN 模式，或者应该为底层协议做好精确的分流路由：

### 方案 A：在代理软件中配置 Bypass 规则（推荐）
在代理软件的路由规则（Rules）中，将目标服务器的 IP 强制指定为 `DIRECT`（直连）。
例如在 Clash 配置文件中添加：
```yaml
rules:
  - IP-CIDR,154.36.155.185/32,DIRECT
  # 或者将默认 22 端口流量全部直连
  - DST-PORT,22,DIRECT
```
这样，发往 22 端口的流量会绕过 TUN 虚拟网卡的接管，走物理网卡直接出去。

### 方案 B：使用 SSH 专用的 ProxyCommand 配合 SOCKS5
关闭代理的 TUN 模式（保留系统级或 SOCKS5 代理），然后在 `~/.ssh/config` 中为特定的服务器配置走代理。这是最优雅、最符合 Linux 哲学的做法：
```text
Host 154.36.155.185
    User root
    # 假设本地代理提供 7890 端口的 socks5 服务
    ProxyCommand nc -x 127.0.0.1:7890 %h %p
```
*注：前提是你的代理节点允许 22 端口的流量。如果节点封禁了 22 端口，此方法依然无效，只能直连。*

## 💡 总结启发
在排查现代复杂的网络故障时，不能仅局限于 OSI 的四层（TCP）和七层（SSH应用层）。引入了透明代理（TUN）后，**网络拓扑在逻辑上被截断了**。我们看到的日志 `Connection established` 并非端到端的事实，这提醒我们在抓包排查（如 Wireshark）时，要注意区分物理网卡（eth0/en0）和虚拟网卡（utun/tun）上的数据包行为。
