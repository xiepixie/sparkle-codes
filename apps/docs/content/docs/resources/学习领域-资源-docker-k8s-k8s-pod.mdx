## 第一部分：知识点提取与查漏清单

### 1. 课程这段内容的主线

* 目标不是一次性讲完整应用，而是先从一个微服务 Pod 开始，逐步把一个云原生应用部署到 Kubernetes 集群。
* 课程先回顾 Kubernetes、云原生应用、容器、Pod、标签、资源请求与限制，然后再进入 `kubectl` 实操。
* 示例应用是一个“成绩提交”系统，先部署前端 `great-submission-portal`，后续再部署后端 `great-submission-api`。

### 2. Kubernetes 集群的基本角色

* Kubernetes 是运行在多台机器上的容器编排系统，用于自动化部署、扩缩容和管理容器化应用。([Kubernetes][1])
* 集群中有控制平面节点（课程里称 master node）和工作节点。
* 控制平面负责调度等控制逻辑；工作节点实际提供 CPU、内存等资源来运行 Pod。
* 课程强调：开发者面对的是一个统一的集群，而不是逐台机器手工部署。

### 3. 云原生应用与微服务

* 云原生应用通常会拆成多个微服务。
* 每个微服务通常运行在容器中。
* 多个微服务协作，组成完整业务能力。
* 课程举例：电商系统可拆为订单、商品目录、库存等多个服务。
* 本例中应用被拆成两个服务：

  * 前端：`great-submission-portal`
  * 后端：`great-submission-api`
* 前端负责接收用户输入；后端负责处理业务逻辑与数据存储。

### 4. 容器在这里解决什么问题

* 容器打包了应用代码及其依赖，使运行环境更一致。
* 课程强调容器的可移植性：相同镜像可以在不同平台和环境中更稳定地运行。
* 镜像是静态打包结果，容器是镜像运行后的实例。

### 5. Pod 是 Kubernetes 的最小部署单元

* Kubernetes 不是直接“部署容器”，而是部署 Pod。
* Pod 是 Kubernetes 管理工作负载的最小单位。
* 容器需要放进 Pod 中，Kubernetes 才能围绕它做调度、资源分配、重建、自愈等管理。
* 课程中的经验性说法是“通常一个微服务对应一个 Pod，一个 Pod 里主要跑一个主容器”。
* 更准确地说：Pod 是调度、网络和存储共享的边界；很多微服务会按“一服务一 Pod”来建模，但不是语法强制规则。

### 6. Pod 清单的核心结构

课程里围绕 Pod YAML 讲了两类内容：

#### 元数据

* `metadata.name`
* `metadata.labels`

#### 运行时规格

* `spec.containers`
* 容器名 `name`
* 镜像 `image`
* 端口 `ports.containerPort`
* 资源 `resources.requests`
* 资源 `resources.limits`

### 7. 标签与分组

课程重点讲了标签的用途：

* 将 Pod 分到逻辑组中。
* 方便查询、批量操作、删除、扩缩容、日志筛选、服务发现等。

课程里使用了这类标签：

* `app.kubernetes.io/name`
* `app.kubernetes.io/component`
* `app.kubernetes.io/instance`

这里需要补足：

* 这些并不是随意起的键，而是 Kubernetes 官方推荐的一组应用标签约定。它们常用于标识应用名、组件角色、实例名，便于工具和自动化系统理解资源之间的关系。([Kubernetes][2])
* `kubernetes.io` 和 `k8s.io` 命名空间整体上属于保留命名空间，但 `app.kubernetes.io/*` 本身又是官方明确推荐用于应用标识的一组常用标签。([Kubernetes][3])

课程中的标签层次大致是：

* 应用名：属于哪个整体应用
* 组件角色：前端还是后端
* 实例名：同一应用的不同部署实例

### 8. 容器端口

* 课程中前端容器监听 `5001` 端口。
* 在 Pod 清单中通过 `containerPort: 5001` 描述容器对外提供的端口。
* 课程说“Pod 会自动为集群内部流量暴露此端口”，更准确地说：

  * `containerPort` 主要是声明性信息，便于阅读和某些工具使用；
  * 容器本身只要监听了该端口，Pod 内网络就能访问；
  * 若要让其他 Pod 通过稳定入口访问，通常还需要 `Service`，后续课程大概率会讲到。

### 9. 资源请求与资源限制

课程围绕 `requests` 和 `limits` 讲了很多内容。

#### 请求 `requests`

* 表示容器最低需要多少资源。
* 调度器会根据请求值决定 Pod 能放到哪个节点上。([Kubernetes][4])
* 课程示例给前端设置：

  * CPU：`200m`
  * Memory：`128Mi` 左右的量级（转录里“128字节”显然是口误，应为内存单位如 `128Mi`）

#### 限制 `limits`

* 表示容器最多可使用多少资源。
* 对 CPU 和内存都可以设限制；Kubernetes 文档明确支持为容器设置 CPU limit 和 memory limit。([Kubernetes][4])

#### 请求与限制的语义

* `request` 用来参与调度，影响 Pod 被放到哪里。([Kubernetes][4])
* `limit` 由运行时执行约束。对 CPU，超过限制会被节流；对内存，超过限制通常会触发 OOM 处理而导致容器被杀掉。([Kubernetes][4])
* 课程里说“CPU 是可压缩资源，内存不可压缩”，这属于常见的工程表述，核心意思是：

  * CPU 不够时通常是变慢、被限速；
  * 内存超限更容易导致进程被杀。

#### 课程里的一个观点需要校正

* 视频讲“CPU 通常不需要设置限制”，这是实践倾向，不是 Kubernetes 规则。
* 官方文档并没有说“不应设置 CPU limit”；只说明 CPU limit 会生效并限制上限。([Kubernetes][5])
* 实际工程里是否设置 CPU limit，要看团队策略、工作负载类型和平台规范，不能当成通用结论。

### 10. 请求不能低于限制

* 课程中故意把值改得很夸张，并出现“请求不能低于限制”的报错。
* 这是合理约束：资源配置必须满足 `request <= limit`。
* 如果请求值比限制值大，清单无效，无法正确创建。

### 11. 资源不足导致 Pending

* 课程把 CPU 和内存请求调到非常大。
* 结果 Pod 一直处于 `Pending`。
* `kubectl describe pod` 中会看到类似：

  * 节点不可用
  * CPU 不足
  * 内存不足
* 这正体现了调度器基于 `requests` 选择节点：节点没有足够可分配资源，Pod 就无法调度。([Kubernetes][4])

### 12. `kubectl` 基本命令

课程里涉及的命令包括：

#### 创建/更新资源

```bash
kubectl apply -f great-submission-portal-pod.yaml
```

#### 查看 Pod

```bash
kubectl get pods
```

#### 查看 Pod 详情

```bash
kubectl describe pod great-submission-portal
```

#### 查看日志

单容器 Pod：

```bash
kubectl logs great-submission-portal
kubectl logs -f great-submission-portal
```

多容器 Pod：

```bash
kubectl logs -f great-submission-portal -c great-submission-portal
kubectl logs -f great-submission-portal -c great-submission-portal-health-checker
```

当 Pod 只有一个容器时，可以省略 `-c`；如果有多个容器，就应指定容器名。([Kubernetes][6])

#### 删除 Pod

按名称删除：

```bash
kubectl delete pod great-submission-portal
```

按标签删除：

```bash
kubectl delete pod -l app.kubernetes.io/name=great-submission
```

### 13. 标签选择器

* 课程演示了 `-l` 标签选择器。
* 可以通过标签筛选一组资源，再做删除、查看等操作。
* 这是标签存在的重要价值之一。Kubernetes 标签就是为对象分组和选择而设计的。([Kubernetes][7])

### 14. 端口转发 `kubectl port-forward`

课程中为了在本机浏览器访问 Pod，使用了端口转发：

```bash
kubectl port-forward pod/great-submission-portal 8080:5001
```

或简写为：

```bash
kubectl port-forward great-submission-portal 8080:5001
```

含义：

* 本地访问 `localhost:8080`
* 请求被转发到 Pod 的 `5001` 端口
* 适合本地调试、演示、临时访问
* 不是生产环境对外暴露服务的常规方式

### 15. 多容器 Pod 与 sidecar

课程最后讲了为什么一个 Pod 有时会放多个容器。

#### 不适合放在同一个 Pod 的情况

* 两个彼此独立的业务微服务，例如前端和后端。
* 它们需要独立发布、独立扩缩容、独立故障处理。
* 这类服务通常不应硬塞进同一个 Pod。

#### 适合放在同一个 Pod 的情况

* 一个主容器加一个依附型辅助容器。
* 课程例子是：

  * 主容器：`great-submission-portal`
  * sidecar：`great-submission-portal-health-checker`

#### 共享特性

同一个 Pod 内多个容器：

* 共享网络命名空间
* 可以通过 `localhost` 互相访问
* 共享部分存储与生命周期上下文

Kubernetes 官方文档明确说明，sidecar 与主容器共享网络和存储命名空间，因此适合做紧密协作。([Kubernetes][8])

课程中 sidecar 通过 `localhost:5001` 持续请求主容器的健康端点，这正是同 Pod 共享网络的直接体现。([Kubernetes][8])

### 16. 关于 sidecar 的一个版本补充

* 课程采用的是“普通多容器 Pod + sidecar 模式”的讲法。
* 新版 Kubernetes 还引入了原生 sidecar 容器相关能力，语义比旧做法更细。官方文档提到 sidecar 容器在新机制下可以有更独立的启动/停止行为。([Kubernetes][8])
* 但本课的理解重点仍然是：

  * sidecar 是辅助主容器的；
  * 它不是独立业务服务；
  * 它因为强依赖主容器而适合同 Pod 部署。

### 17. 转录稿中的明显口误或需要修正之处

* “128字节内存”应理解为类似 `128Mi`，不可能真是 128B。
* “5000或0.1”应是 `127.0.0.1` 一类的本机地址口误。
* “Cube tl / cube l / cube ctl” 都是 `kubectl` 的转录错误。
* “主节点”是课程里的旧称，现代官方文档通常使用 control plane 节点。
* “Pod 自动暴露端口”应谨慎理解，`containerPort` 不等于自动创建 `Service`。

## 第二部分：整理后的讲义正文

## Kubernetes 中为什么不是直接部署容器，而是部署 Pod

这一节课的核心，不是把 YAML 写出来就结束，而是理解 Kubernetes 到底把什么当成“最小可管理对象”。课程先从一个常见误解切入：Kubernetes 虽然是容器编排平台，但它真正调度和管理的对象并不是裸容器，而是 Pod。Kubernetes 运行在一个由多台机器组成的集群上，控制平面负责调度和控制逻辑，工作节点负责提供实际的计算资源。开发者提交的是期望状态，Kubernetes 决定应用最终在哪台节点上运行，并持续维持这种状态。([Kubernetes][1])

这也是为什么课程在正式部署前，先把“容器”“微服务”“Pod”重新捋了一遍。容器解决的是打包和运行一致性问题：把应用代码和依赖一起封装，减少环境差异。云原生应用则常常把业务拆成多个微服务，每个微服务往往以一个容器镜像的形式交付。可是在 Kubernetes 中，容器还需要一个更高一层的运行载体，这个载体就是 Pod。Pod 才是调度、网络、资源和生命周期管理的基本边界。

很多入门课程会把 Pod 说成“像原子一样的最小单位”，这个比喻可以帮助记忆，但要注意它不是在说 Pod 只能放一个容器，而是在说 Kubernetes 以 Pod 为管理单位。也正因为如此，课程里强调“通常一个微服务对应一个 Pod”，这在工程上是常见建模方式：一个业务职责清晰的服务，通常独立占有一个 Pod，方便单独发布、扩缩容和排障。

## 这个示例应用怎样映射到 Kubernetes 对象

课程里的示例应用是一个成绩提交系统，先部署前端门户 `great-submission-portal`，再部署后端接口 `great-submission-api`。前端负责接收用户提交的数据，后端负责处理业务逻辑和存储。这里的重点不是业务本身，而是让你看到一个云原生应用如何从“微服务 + 容器镜像”的交付方式，落到 Kubernetes 的 Pod 清单上。

前端服务已经被预先打包成 Docker 镜像。镜像本身只是静态产物，只有在 Kubernetes 节点上被创建为容器，服务才真正开始运行。而容器不会直接挂在集群里，它必须出现在某个 Pod 的 `spec.containers` 中。于是，课程先为前端服务准备一个 Pod YAML，这样集群才能理解：这个工作负载叫什么名字、属于哪个应用、需要什么资源、该监听哪个端口。

## Pod 清单要表达两类信息：身份与运行需求

一个 Pod 清单可以先粗略分成两部分：`metadata` 和 `spec`。前者回答“你是谁”，后者回答“你怎么运行”。

在 `metadata` 中，最直接的是 Pod 名称，例如：

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: great-submission-portal
```

名称解决的是对象级唯一标识问题，但在 Kubernetes 里，真正决定可筛选性和可批量操作性的，往往不是名字，而是标签。课程这里讲得很对：如果你未来需要按应用、按组件角色、按实例批量找出一组 Pod，标签比名字重要得多。

课程使用了 `app.kubernetes.io/name`、`app.kubernetes.io/component`、`app.kubernetes.io/instance` 这样的键。这不是随手起的命名风格，而是 Kubernetes 官方推荐的一组应用标签约定。它们的目的，是让资源的应用归属、组件角色和实例身份更清晰，也更利于工具识别。([Kubernetes][2])

一个更自然的写法大致会像这样：

```yaml
metadata:
  name: great-submission-portal
  labels:
    app.kubernetes.io/name: great-submission
    app.kubernetes.io/component: frontend
    app.kubernetes.io/instance: great-submission-portal
```

这里可以看出三个层次。`name` 用来说明它属于哪个整体应用，`component` 用来区分前端和后端这类角色，`instance` 则进一步标识具体实例。这样做的好处不是“好看”，而是你后面真的可以基于这些标签做选择器查询，比如删除某一组 Pod，或者查看某一类组件的日志。Kubernetes 的标签机制本来就是为对象分组和选择而设计的。([Kubernetes][7])

## 容器镜像、端口和资源：Pod 真正的运行规格

进入 `spec` 之后，才是这个 Pod 真正要跑什么。课程中的前端容器可以整理成下面这种形式：

```yaml
spec:
  containers:
    - name: great-submission-portal
      image: <你的镜像名>
      ports:
        - containerPort: 5001
      resources:
        requests:
          cpu: "200m"
          memory: "128Mi"
        limits:
          memory: "128Mi"
```

先看镜像。镜像是应用代码和依赖的打包快照，容器是镜像运行后的实例。Kubernetes 不关心你这个镜像是 Python、Java 还是 Node.js，它只关心：我能否在某个节点上拉取这个镜像、创建这个容器，并满足它的运行约束。

再看端口。课程里前端服务监听 `5001`，所以在容器描述中加入 `containerPort: 5001`。这里很适合顺手纠正一个初学者误区：`containerPort` 主要是声明性配置，它不会自动替你创建一个面向集群的稳定访问入口。容器只要自己在该端口监听，Pod 内网络就能访问；但如果你要让其他 Pod 通过稳定虚拟地址访问它，通常还需要 `Service`。这一点在后续讲服务发现时会很重要。

资源配置是这节课最有价值的部分之一。课程强调要区分 `requests` 和 `limits`。这两个字段都写在容器级资源配置里，但职责不同。`requests` 是“至少需要多少”，调度器会根据它判断节点是否有足够资源容纳这个 Pod。官方文档明确说明，调度器会使用请求值来决定把 Pod 放到哪个节点。([Kubernetes][4]) `limits` 则是“最多允许用多少”，由节点上的运行时和 kubelet 负责执行约束。([Kubernetes][4])

这也是为什么课程里把资源请求故意改得很夸张之后，Pod 会一直卡在 `Pending`。不是容器“坏了”，而是调度阶段就失败了：集群里没有任何节点满足这么大的 CPU 和内存请求，所以它根本放不下去。你在 `kubectl describe pod` 里看到的 `Insufficient cpu`、`Insufficient memory`，本质上就是调度器在解释它为什么找不到合适节点。([Kubernetes][4])

## 为什么内存限制更敏感，CPU 限制更有争议

课程用了一个很常见的经验说法：CPU 是“可压缩”的，内存不是。这个表述在入门阶段很好理解。CPU 不够时，容器通常只是被节流，运行变慢；内存如果冲破限制，更可能直接触发 OOM，被系统杀掉。官方文档也明确区分了两类资源的限制行为：CPU 超过限制会被限制使用，内存超过限制则会触发更严厉的运行时后果。([Kubernetes][4])

课程进一步得出一个实践建议：内存通常要设 limit，CPU 不一定要设 limit。这个建议在很多团队里确实存在，因为对 CPU 限制过严，有时会让程序平白变慢；而不给内存上限，风险往往更大。但要把它看成实践偏好，不是 Kubernetes 的硬规则。Kubernetes 官方同样支持设置 CPU limit，也没有说“不应设置”。([Kubernetes][5])

所以更稳妥的工程判断是：
如果你所在平台、命名空间策略或团队治理要求容器必须写全 `requests/limits`，那就按平台规范来；如果是自建环境，要结合压测、监控和应用特征来决定 CPU 上限该不该设、多紧合适。课程里关闭 VS Code 插件对“未设置 CPU limit”的提示，本质上是在绕过编辑器规则，不是在改变 Kubernetes 行为。

另一个必须记住的约束是：`request` 不能大于 `limit`。课程里把值改乱之后遇到校验错误，这不是特殊情况，而是资源语义本身决定的。既然 `request` 表示最低保证，`limit` 表示最高上限，最低值当然不应高于上限。

## 从 YAML 到运行中的 Pod：`kubectl` 在做什么

课程里的操作路径很适合作为第一次上手的最小闭环：

先应用清单：

```bash
kubectl apply -f great-submission-portal-pod.yaml
```

然后查看 Pod 是否创建出来：

```bash
kubectl get pods
```

如果 Pod 还没起来，可以继续看详情：

```bash
kubectl describe pod great-submission-portal
```

这时你通常会看到事件、镜像拉取状态、调度信息和资源请求等内容。`describe` 的价值在于，它不是简单告诉你“失败了”，而是告诉你失败在哪个阶段：是镜像拉取失败、端口配置问题、资源不足，还是探针异常。

等容器真正起来后，可以用日志验证应用是否正常运行：

```bash
kubectl logs great-submission-portal
kubectl logs -f great-submission-portal
```

其中 `-f` 表示持续流式跟随日志。官方命令文档也说明了：如果 Pod 只有一个容器，容器名可以省略；如果是多容器 Pod，就应该用 `-c` 指定具体容器。([Kubernetes][6])

这节课还用了一个很实用的调试技巧：端口转发。

```bash
kubectl port-forward pod/great-submission-portal 8080:5001
```

这条命令的意义不是“把服务正式发布出去”，而是临时把本地 `8080` 和 Pod 内的 `5001` 接起来。这样你在浏览器访问 `localhost:8080` 时，请求会被转发到 Pod 中的应用端口。它很适合开发调试、课程演示和临时验证，但不该替代真正的服务暴露方式。

## 标签为什么重要：它不是装饰，而是后续操作的入口

课程中间专门演示了按标签删除 Pod，这一段非常值得保留。刚接触 Kubernetes 的人容易觉得标签只是“多写几个键值对”，但实际上，标签是后续所有组合操作的入口。你可以不靠对象名，而是靠逻辑身份来选资源。

例如：

```bash
kubectl delete pod -l app.kubernetes.io/name=great-submission
```

这类命令的价值在单个 Pod 场景下看似不大，但只要对象数量一多，标签选择器就会立刻变得重要。无论是 `kubectl logs -l ...`、`kubectl delete -l ...`，还是 Service 通过 selector 发现后端 Pod，背后都是同一个机制：先打好稳定的标签，再通过选择器把一组对象找出来。([Kubernetes][7])

课程中按“应用 → 组件 → 实例”的层次打标签，是很适合教学的。因为它对应了三个常见查询维度：
你可以按整个应用筛，按前后端角色筛，也可以按某个具体实例筛。这个层次不是唯一标准，但它体现了一条很实用的原则：标签要服务于未来的查询和运维动作，而不是只为当前 YAML 好看。

## 为什么前端和后端不该塞进同一个 Pod

课程最后讲到一个非常关键的设计判断：虽然 Pod 可以包含多个容器，但这不意味着“多个服务就应该放到一个 Pod 里”。前端 `great-submission-portal` 和后端 `great-submission-api` 是两个职责独立的业务服务，它们通常要独立扩缩容、独立发布、独立回滚。如果把它们塞进同一个 Pod，等于把两个本该独立治理的生命周期绑死了。

这是学习 Kubernetes 时很容易忽略的点。很多人一看到“Pod 能有多个容器”，就会误以为“我有两个互相调用的服务，那就一起放”。实际上，多容器 Pod 更适合强耦合、辅助型、离不开主容器的场景，例如：

* 日志收集 sidecar
* 代理 sidecar
* 配置同步 sidecar
* 健康监控 sidecar

这些辅助容器不是独立业务单元，它们的存在是为了给主容器提供额外能力。课程中的 `great-submission-portal-health-checker` 就属于这个思路：它不是另一个业务服务，而是围绕主容器做健康检查和状态输出。

## 多容器 Pod 的真正价值：共享网络和本地协作

课程里 sidecar 持续访问主容器的健康检查端点，这一段很适合用来理解同 Pod 容器为什么方便。Kubernetes 官方文档明确指出，sidecar 与主容器共享同一个网络命名空间和存储命名空间，因此它们可以非常紧密地协作。([Kubernetes][8])

对这节课来说，最重要的体现就是：同一个 Pod 里的两个容器可以通过 `localhost` 通信。也就是说，健康检查器不需要通过 Service 找前端容器，也不需要知道集群里的 Pod IP 变化，它直接请求 `localhost:5001` 就行。因为从网络视角看，它们就在同一个 Pod 网络上下文里。([Kubernetes][8])

课程中这个 Pod 可以整理为：

```yaml
spec:
  containers:
    - name: great-submission-portal
      image: <portal-image>
      ports:
        - containerPort: 5001
      resources:
        requests:
          cpu: "200m"
          memory: "128Mi"
        limits:
          memory: "128Mi"

    - name: great-submission-portal-health-checker
      image: <health-checker-image>
      resources:
        requests:
          cpu: "200m"
          memory: "128Mi"
        limits:
          memory: "128Mi"
```

这里第二个容器没有暴露 `containerPort`，因为它不是被外部访问的 Web 服务，它的职责是主动请求主容器，而不是提供对外入口。

部署完成后，再看日志就要注意多容器 Pod 的语法了：

```bash
kubectl logs -f great-submission-portal -c great-submission-portal
kubectl logs -f great-submission-portal -c great-submission-portal-health-checker
```

同一个 Pod 内有多个容器时，必须明确你想看哪一个，否则日志命令就不再足够明确。官方命令参考也特别指出了这一点。([Kubernetes][6])

## 关于 sidecar，还需要知道一层版本语义

课程中的讲法基于传统的多容器 Pod 模式：在 `spec.containers` 里并排定义主容器和辅助容器。这种模式今天仍然大量存在，也完全能表达课程示例。

但从较新的 Kubernetes 版本开始，官方已经引入了原生 sidecar 相关能力，sidecar 在启动、停止和重启语义上可以更细分。官方文档明确提到，sidecar 与主容器共享网络和存储，并且在新版机制下可以拥有更独立的行为。([Kubernetes][8])

这并不影响本课入门结论，但能帮助你避免把课程表述绝对化。你可以保留一个简单判断：
本课讲的是“为什么有些辅助容器适合同 Pod 部署”；至于 Kubernetes 新版对 sidecar 生命周期做了哪些增强，那是进阶话题。

## 这节课真正想让你建立的工程直觉

如果把这节课只看成“会写一个 Pod YAML”，那价值会很有限。它真正要你形成的，是几个很重要的工程判断。

第一，Kubernetes 管理的是 Pod，不是裸容器。你写 YAML 时要始终想清楚：这个工作负载应该以什么 Pod 边界存在。

第二，标签不是装饰，而是未来批量管理、服务发现和运维筛选的基础。清单一开始写乱了，后面会越来越难管。

第三，资源请求不是“随便写个数”，它决定调度结果。资源限制也不是“越严格越好”，而是要理解 CPU 与内存的行为差异，再结合应用特征和平台规范来定。([Kubernetes][4])

第四，多容器 Pod 不是拿来塞多个业务服务的，而是拿来承载紧密协作的主容器与辅助容器。只要两个容器需要独立扩缩容、独立发布，通常就不该绑在同一个 Pod 里。

把这些判断建立起来，后面学 Deployment、Service、Ingress、探针、ConfigMap、滚动更新时，很多设计就会顺理成章。

---

## 第三部分：最后总结

1. **Kubernetes 的最小部署与管理单位是 Pod，不是容器。** 容器要放进 Pod，Kubernetes 才能围绕它做调度、资源控制和生命周期管理。

2. **标签是后续管理动作的入口。** `app.kubernetes.io/name`、`component`、`instance` 这类官方推荐标签，能让你按应用、角色、实例稳定筛选资源。([Kubernetes][2])

3. **`requests` 决定 Pod 能不能被调度，`limits` 决定容器最多能用多少。** 请求过大时，Pod 会一直 `Pending`；限制配置不合理时，会带来节流或 OOM 等后果。([Kubernetes][4])

4. **CPU limit 是否一定要设，没有统一答案。** 课程给的是一种常见实践偏好，不是 Kubernetes 硬规则；要结合平台规范、应用特征和性能测试来定。([Kubernetes][4])

5. **`containerPort` 不等于自动拥有稳定服务入口。** 本地调试可以用 `kubectl port-forward`，而正式的服务访问通常还要依赖 `Service` 等对象。

6. **多容器 Pod 适合“主容器 + 辅助容器”，不适合随意把两个独立业务服务绑在一起。** sidecar 的价值在于与主容器共享网络命名空间，可通过 `localhost` 紧密协作。([Kubernetes][8])

7. **排错时优先看三个地方：`kubectl get pods`、`kubectl describe pod`、`kubectl logs`。** 它们分别回答“状态是什么”“为什么这样”“应用自己说了什么”，足够覆盖大多数入门场景。
