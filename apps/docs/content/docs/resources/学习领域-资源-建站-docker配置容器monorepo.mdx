宿主机创建或修改 `/etc/docker/daemon.json`：

&#123;  
  "dns": ["1.1.1.1", "8.8.8.8"]  
&#125;
这个 `postgresql://postgres:postgres@localhost:5432/build-time-dummy` 确实是一个“看起来很奇怪”的设置，但它在 **Docker 自动化构建**中至关重要。

### 核心原因：骗过 Next.js 的“构建检查”

1. **Next.js 的构建预检查 (Build-time Check)**：
    
    - 当你运行 `next build`（也就是你日志里的 `Creating an optimized production build`）时，Next.js 会尝试编译所有的页面。
    - **问题来了**：如果你的页面代码里引用了数据库（比如调用了 Drizzle 或者获取初始数据），Next.js 在构建阶段有时会**尝试检测数据库连接**是否合法，或者通过读取数据库来生成一些静态页面（SSG）。
    - **如果没有地址**：如果构建时环境变量里完全没有 `DATABASE_URL`，很多数据库插件（比如 Prisma 或 Drizzle 相关组件）会直接报错退出，导致构建无法进行。
2. **为什么是 Dummy (假地址)？**：
    
    - 我们在构建 Docker 镜像时（也就是你在日志里看到的这一步），**真正的生产环境数据库还没连上呢**。真正的密码和地址都在你服务器的 `.env.production` 里，而构建过程中是拿不到那个包含千万资产的真实配置的。
    - 所以我们给它一个“假地址”（`build-time-dummy`），就像是给体检医生一个“临时身份证”，目的是**让构建流程先走下去**，不让它因为检测不到环境变量而报错掐断。
3. **最终运行时的替换**：
    
    - 当镜像构建完、容器跑起来的一瞬间，系统会自动把这个“假地址”换成你 `.env.production` 里的**真实 Neon 数据库地址**。
    - Next.js 只有在真正运行的时候才会用到那个真地址去存取你的千万数据。

当 Docker 跑完之后，你直接访问域名，确实是**全新的**！

但考虑到 Web 开发的特性，有几个层级的“刷新”建议你了解一下，以确保你看到的是最新的成果：

### 1. 服务端：实时生效

- **容器层面**：只要 `docker compose up -d` 命令完成，旧的 Docker 容器就被销毁了，新的容器已经接管了流量。
- **数据库 (SQL 修复)**：由于我们的 SQL 逻辑补丁已经在新的 Node.js 进程里跑了，只要你刷新页面触发数据库查询，SQL 报错就会立刻消失。

### 2. 浏览器端：建议“强刷”

虽然服务器是新的，但你的**浏览器（Chrome / Safari）**为了省流量，会本地缓存一些 CSS、JS 以及图片资源。

- **建议操作**：访问域名后，按住 `Cmd + Shift + R` (Mac) 或者 `Ctrl + F5` (Windows) 进行**硬刷新 (Hard Reload)**。
- **原因**：这会强制浏览器丢弃本地缓存，重新去向你的新 Docker 容器申请最新的前端代码，尤其是我们的右上角导航链接（Navbar）。

### 3. Next.js 路由缓存 (Client Router Cache)

- **表现**：如果你已经在旧页面停留了很久，直接点击页面内的 Link 跳转，有时 Next.js 会尝试复用之前的页面预加载数据。
- **解决**：**直接在地址栏回车重新载入一次镜像**，或者按上述说的“强刷”，就能彻底重置 Client-side Cache。

### 4. 1Panel / Nginx 层 (通常不需要刷新)

- 1Panel 的反向代理如果不开启特殊的“静态资源缓存” (FastCGI Cache)，它是直接透传流量的。
- **结论**：如果你改了反向代理配置（比如加了 `/docs`），只要保存了，Nginx 就会即时生效，不需要额外刷新。
- 这是一个非常关键的架构决策。从**技术稳定性**和**维护成本**来看，回答是：**是的，挂载在 `docs.sparkle.codes` 这种子域名上会“干净”得多。**

以下是深度对比，帮助你做最后決定：

### 1. 为什么子域名 (`docs.sparkle.codes`) 更优？

- **完全消除路径冲突**：
    - 目前使用 `sparkle.codes/docs` 最大的痛苦源于 **Next.js 的 `basePath`**。
    - Next.js 的 `basePath` 会自动给所有 `<Link>`、静态资源（`/_next/static/...`）加上 `/docs` 前缀。如果你同时在应用内部、代码里或代理服务器里也加了前缀，极其容易出现“双重前缀”或“资源 404”的问题。
    - 如果用子域名，`apps/docs` 就是一个**普通的根路径应用**，不需要配置 `basePath`，也不需要特殊的 `rewrites`，所有逻辑回归到最简单的状态。
- **静态资源加载更顺畅**：
    - 主站和文档站的资源（JS/CSS）互不干扰，不会因为 `sparkle.codes/docs/_next/...` 的路径转发导致的 404 或加载缓慢，CDN 缓存命中率也会更高。
- **独立部署与扩展**：
    - 你可以独立升级文档站的镜像，而不用担心主站的 `rewrites` 规则是否会因为主站更新而失效。

### 2. 为什么有人坚持用 `sparkle.codes/docs`（路径模式）？

- **SEO 权重集中**：搜索引擎（如 Google）通常认为 `/docs` 是主站的一部分，权重共享更好。不过对于技术文档，子域名的权重影响在现代 SEO 中已经非常小了。
- **品牌统一感**：看起来更像是一个整体。

### 3. 如果由于各种原因（如已经发布了大量链接）必须保留 `/docs`：

那么目前的方案（使用我刚才提到的“兼容层路由” + 严谨的 Docker 资源拷贝）是可以跑通的，但每当升级 Next.js 或 Fumadocs 时，你都需要仔细检查 `basePath` 的行为是否有变化。

### 4. 总结建议

- **如果你追求“一劳永逸”且不介意子域名带来的极小 SEO 差异**：**强烈建议改为 `docs.sparkle.codes`**。
    - 这会让你从繁琐的路径匹配和 404 排查中彻底解脱。
    - 配置改动：去掉 `next.config.mjs` 里的 `basePath`，设置 `source.ts` 里的 `baseUrl` 为 `/`。
- **如果你希望保持主站域名完整性**：我们需要继续打磨目前的 `/docs` 路径方案，确保 **Next.js `basePath`**、**Fumadocs `baseUrl`** 和 **Nginx/Docker 代理** 这三者逻辑完全咬合。
